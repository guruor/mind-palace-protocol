# Mind Palace Protocol v0.9.4

## Outcome

This release makes common memory a **state-plus-awareness** layer: one active
Source Pointer plus a compact, self-describing **awareness core** rendered on
that single release record. A client resolves the pointer, reads the awareness
core to become aware of the Mind Palace and operate correctly, and fetches
byte-exact schemas, templates, and document-type contracts from the immutable
Git release only when it needs them.

## Changes

- Materialize the derived awareness core (`protocol/awareness-core.md`) on the
  active release record, built deterministically from the `core` resources
  (General Guide, selected methodology, storage binding, manifest summary).
- Document that the awareness core is a **projection, not an authority**:
  rendering can normalize formatting, so byte-exact contracts are never stored
  in common memory and always fetched and verified from the immutable release.
- Move `schemas/artifact.schema.json` from `core` to `on-demand` because it is a
  byte-exact contract; validators now enforce the resource-class criterion.
- Add a first-read contract ("Becoming Aware") so awareness is a verifiable
  state, not an implicit consequence of scattered files.
- Record the product rationale ("Why this product and shape"), the
  distribution-and-awareness split, methodology resolution, and extension
  boundaries in `docs/architecture.md`.
- Align client adapters (Agent Skill and hosted-chat managed block) to read the
  awareness core and fetch exact contracts from the immutable source on demand.
- Add `awareness` to the common-memory installation schema and state machine,
  including a conflict when the awareness digest differs.
- Update the common-memory write plan to account for awareness-content bytes and
  to carry the awareness digest for staged verification.

## Compatibility

Document and migration semantics remain compatible with `v0.9.3`. The
common-memory representation changes during the experimental `0.y.z` series:
release records now render the awareness core instead of being blank pointer
records. Clients that already resolve the active Source Pointer continue to work
and gain the ability to read guidance directly from common memory. Legacy
component, bundle, and payload record shapes remain recognizable until cleanup.

## Rollback

Recreate a prior Source Pointer and awareness core from its immutable Git tag,
verify the Release Index and core digest, and activate it through the normal
approval path. Do not retain old protocol projections solely for rollback.
